# VeriLens — Project Requirements

## 1. Problem Statement

VeriLens is a browser extension supported by a cloud-deployed API that estimates whether a given piece of text was generated by an AI system or written by a human. Since AI-text detectors can make mistakes when analyzing human-written or AI-generated content, VeriLens will communicate uncertainty transparently rather than presenting its predictions as definitive proof.

The goal is to help users make more informed judgments about online text while clearly explaining the limitations of automated detection.

## 2. In Scope — Minimum Viable Product (MVP)

The following features are included in the initial version of VeriLens:
 
 - **AI-text detection (English only):** Analyze submitted English text and return one of three labels (`likely_ai`, `likely_human`, or `uncertain`) together with an AI-likelihood score. Text shorter than a minimum length (to be set after testing) always returns `uncertain`.
- **Measured explanations:** Each result includes reasons derived from measured text features, such as sentence-length variation and how predictable the text is. Explanations are not free-form text written by a language model.
- **Browser extension:** Provide a user interface for submitting or selecting text and viewing detection results.
- **Cloud-deployed API:** Expose the detection functionality through an API deployed to a cloud environment.
- **MLOps tracking:** Track relevant model versions, experiments, configurations, and evaluation results to support reproducibility.
- **Model evaluation:** Evaluate detection performance using appropriate datasets, held-out generators, and clearly defined metrics.
- **Transparent reporting:** Communicate uncertainty and known limitations alongside predictions.

## 3. Out of Scope — Future Work

The following features are excluded from the initial MVP and may be considered for future development, depending on time and resources:

- **Claim verification:** Checking whether factual claims in a text are accurate.
- **Image detection:** Detecting AI-generated or manipulated images.
- **Source analysis:** Analyzing the origin, provenance, or authorship history of text.
- **Additional detection capabilities:** Extending the system to other content types or detection methods beyond the initial text-focused scope.

These features will only be considered for the MVP if the core detection, deployment, and evaluation requirements are completed and sufficient time remains.

## 4. Success Criteria

VeriLens will be evaluated using a baseline model before final performance targets are established. Numerical targets will be defined after the baseline evaluation to ensure that they are informed by measured performance rather than arbitrary assumptions.

| Metric | Definition | Target |
|---|---|---|
| AUROC | Area under the receiver operating characteristic curve; measures the model's ability to distinguish between classes across thresholds. | TBD |
| True-positive rate at 1% false-positive rate | Proportion of AI-generated samples correctly identified when the false-positive rate on human-written samples is held at 1%. | TBD |
| Held-out generator performance | Detection performance on AI generators excluded from training and model selection. | TBD |
| Calibration | Whether predicted likelihoods match reality, for example whether samples scored around 80% are AI-generated about 80% of the time. | TBD |
| Coverage | Share of inputs that receive a definite label instead of `uncertain`. Always reported alongside accuracy. | TBD |
| Fairness check | False-positive rate on human-written text by non-native English writers, compared with native writers. | TBD |






### Evaluation Requirements

- Establish and document a baseline before setting final numerical performance targets.
- Keep test data separate from training and model-selection data.
- Include held-out AI generators to assess generalization to previously unseen generators.
- Report class balance, dataset sources, evaluation methodology, and relevant limitations.
- Report false positives and false negatives in addition to aggregate metrics.
- Document the final targets and compare them with measured results after evaluation.
- Make every reported metric reproducible: document the dataset, model version, and procedure well enough that the numbers can be regenerated.

## 5. Limitations Statement

### Full User-Facing Notice

"VeriLens provides an estimate of whether text may have been generated by AI. It is not a definitive authorship test, and its predictions may be incorrect. Human-written text may be incorrectly flagged as AI-generated (a false positive), and AI-generated text may be classified as human-written (a false negative). Results can vary depending on the text, writing style, length, and AI generator. Do not use a VeriLens result as the sole basis for decisions about academic integrity, employment, reputation, or other consequential matters."

### Short Notice (shown in the result panel)

"This is an estimate, not proof. Results can be wrong, especially for short or edited text."

### Interpretation Guidelines

- A detection result must be presented as an estimate, not proof of authorship.
- Confidence scores, if provided, must not be described as a guarantee that a prediction is correct.
- The system must acknowledge that performance may differ across datasets, languages, writing styles, and generators.
- Where evidence is insufficient or the input is unsuitable for reliable analysis, the system should communicate that limitation rather than imply certainty.
- Evaluation results must be interpreted in the context of the tested data and conditions.
## 6. Non-Functional Requirements

### Privacy

- User text is not stored. The backend logs only metadata: text length, score, label, response time, and model version.
- The extension shows a first-run consent message explaining that selected text is sent to the VeriLens API for analysis.
- Text is never sent to third-party services without being disclosed in that message.

### Cost

- The project must run using free tools, free tiers, and student credits only.
- Model training uses free Colab or Kaggle GPUs. The deployed API runs on a CPU-only instance.

### Latency

- The API should return a result within a target response time (to be set after measuring performance on the deployed CPU instance).

## 7. MLOps and Cloud Requirements

Each requirement below is a yes/no check to be confirmed at the end of the project.

- **Containerized:** the API runs inside a Docker container.
- **Cloud-deployed:** the container runs on a cloud platform and the extension can reach it over HTTPS.
- **Automated deployment:** pushing to the main branch triggers automated tests and, if they pass, a deployment (CI/CD).
- **Experiment tracking:** every training and evaluation run is logged with its dataset, settings, and metrics.
- **Traceability:** every API result includes a model version that maps back to a specific logged experiment run.
- **Monitoring:** the service records request count, response time, and error rate, and these can be viewed.
- **Health check:** the API has an endpoint that reports whether the service is running.
## 8. Constraints

- **Team:** solo project.
- **Deadline:** end of November 2026.
- **Budget:** free tools, free tiers, and student credits only.
- **Training hardware:** free Colab or Kaggle GPUs. The development laptop has no GPU.
- **Deployment hardware:** CPU-only, which limits how large the deployed model can be.
